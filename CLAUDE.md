# CLAUDE.md — Weekly Football

Постоянный контекст проекта. Читай этот файл в начале каждой сессии. Полное ТЗ лежит в `docs/TZ.md`.

## Что это

Веб-приложение (PWA) для нашей еженедельной игры в футбол: 15–20 человек, обычно суббота 19:00, общение в WhatsApp.

Идея: игроки заранее отмечаются «Иду», все записавшиеся попадают в список игры, организатор делит их на команды (название, цвет), опоздавших докидывает в готовые команды, матч идёт с таймером и live-счётом, статистика копится сама.

**Главная боль, которую решаем:** не тратить время на деление на команды и ожидание опоздавших.

## Роли

- **Организатор** — создаёт группу и игры, делит на команды, ведёт матч.
- **Игрок** — отмечается, смотрит составы, live и статистику.
- **Гость** — смотрит публичную страницу игры.

Деньги и взносы **не** входят в проект. Не добавлять.

## Стек

- Next.js (App Router) + TypeScript, деплой на Vercel
- Tailwind CSS + shadcn/ui, dnd-kit (для команд)
- Supabase: PostgreSQL, Auth, Realtime, RLS
- Vercel Cron Jobs для автоматизации
- WhatsApp: только ссылки `wa.me` и Open Graph превью (без платного API)

Используй актуальные стабильные версии и сверяйся с официальной документацией, а не с памятью.

## Правила работы

1. **Одна фаза за раз.** Фазы описаны ниже и в `docs/TZ.md`. Не начинай следующую, пока в текущей не выполнены все пункты «Готово, когда». Не добавляй функции из других фаз.
2. **Схема БД только через миграции** в `supabase/migrations/`. Никаких ручных правок через панель Supabase.
3. **Безопасность на уровне базы:** RLS включён на каждой таблице. Права организатора проверяются в политиках, а не только в интерфейсе.
4. **Секреты** только в `.env.local` и в переменных Vercel. Никогда не коммить ключи. `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере.
5. **Mobile-first.** 95% пользователей с телефона. Проверять на ширине 375 px, крупные кнопки (минимум 44 px).
6. **Язык интерфейса — русский.** Код, имена переменных и коммиты — английский.
7. **Маленькие коммиты** после каждого блока задач, понятные сообщения (`feat:`, `fix:`, `chore:`).
8. Если задача требует действий вне кода (создать проект в Supabase, включить провайдер входа, задать переменные в Vercel), **не выдумывай результат**: остановись и дай пошаговую инструкцию для человека.
9. Если требование в ТЗ неясно или противоречиво, задай один короткий вопрос, а не угадывай.

## Заметки по ходу работы

_Сюда записывай решения, которые влияют на следующие фазы._

### Фаза 1
- **Next.js 16**: `middleware.ts` переименован в `src/proxy.ts` (функция `proxy`). Логика обновления сессии — в `src/lib/supabase/middleware.ts`. Перед работой с Next читать `node_modules/next/dist/docs/` (см. @AGENTS.md).
- `npm run typecheck` = `next typegen && tsc --noEmit` — глобальные `PageProps`/`LayoutProps` генерируются Next.
- shadcn использует стиль `base-nova` (Base UI, не Radix) и пакет `cn`. Размеры `Button`/`Input` в `src/components/ui` подняты до 44 px (h-11) — не откатывать при обновлении компонентов.
- Тёмная тема только по системной настройке: `dark:` = `@media (prefers-color-scheme: dark)`, класса `.dark` нет.
- Авторизация: сервер проверяет пользователя через `supabase.auth.getClaims()` (не `getSession`). Анонимная сессия создаётся в server action при первом `create_group`/`join_group`.
- Google: `linkIdentity` для анонимных (требует **Manual linking** в Supabase), `signInWithOAuth` для нового устройства. Колбэк — `/auth/callback`.
- «Текущая группа» = последняя, в которую вступил пользователь (`getAppContext` в `src/lib/session.ts`). Переключателя групп нет — добавить, если понадобится несколько групп.
- БД: `insert/delete` в `players`, `groups`, `group_members` с клиента запрещены грантами; всё создание — через `create_group`/`join_group` (security definer). `update` разрешён по колонкам: `players(name, avatar_url, position)`, `groups(name)`, `group_members(role)`. `level` и `rating` игрок сам менять не может — их будут менять организатор (Фаза 3) и статистика (Фаза 5).
- RLS-хелперы лежат в схеме `private` (не видна через API): `is_group_member`, `is_group_organizer`, `shares_group_with`. Использовать их в политиках следующих фаз.
- Триггер не даёт оставить группу без организатора (ошибка `last_organizer`).
- Код приглашения — 8 символов без 0/O/1/I, регистр при вводе не важен.
- `database.types.ts` написан вручную — после изменения схемы перегенерировать `npx supabase gen types typescript`.

### Фаза 2
- **Часовой пояс:** в БД всё `timestamptz` (UTC). У `schedules` и `games` есть `timezone` (по умолчанию `Asia/Almaty`); показ — `formatGameDate(iso, game.timezone)` из `src/lib/datetime.ts` («Сб, 4 окт, 19:00»). Перевод локального времени расписания в UTC делает Postgres (`(date + time) at time zone tz`), для разовых игр — `zonedTimeToUtc` на сервере. `games.timezone` — добавлено сверх ТЗ, чтобы разовые игры тоже знали свой пояс.
- **Cron (Vercel Hobby, раз в сутки, ±1 час):** только `create_upcoming_games(14)` через `/api/cron/create-next` (service role). Всё, что зависит от точного времени, — вручную или по событию. Дополнительно триггер на `schedules` сразу создаёт игры при создании/изменении расписания, поэтому cron — страховка, а не единственный путь.
- При изменении/отключении расписания будущие игры этого расписания **без записавшихся** удаляются и пересоздаются; игры, где уже есть `going`/`waitlist`, не трогаются — организатор отменяет их вручную.
- **Статусы игры:** `signup → closed → signup`, любой → `cancelled` (обратно нельзя). `teams`, `live`, `finished` заведены для Фаз 3–4 — переходы в них добавить в `set_game_status`. «Ближайшая игра» = первая с `starts_at >= now() - 3 ч` и статусом не `finished`.
- **Очередь:** `signups.created_at` = момент последней записи «Иду» (сбрасывается при повторной записи после отказа), порядок листа ожидания — `created_at, player_id`. Лимит защищён `select … for update` по строке игры. Автоперевод из очереди — `private.promote_waitlist`; вызывать его и при увеличении `max_players`, если такое появится.
- `signups` меняются только через `set_signup` / `set_arrival`; `games` — insert организатором (разовые) и `set_game_status`. Прямой `update games` запрещён грантами.
- **Realtime:** `games` и `signups` в публикации `supabase_realtime`. Клиент `GameRealtime` подписывается и делает `router.refresh()` (сервер остаётся источником правды), плюс обновляется при возврате вкладки на экран.
- **OG-превью** `/game/[id]` читает данные через service role (`getGamePreview`) без имён игроков. WhatsApp входит в `htmlLimitedBots` Next — метаданные попадают в `<head>` без стриминга.
- **Realtime-ловушка:** статус `SUBSCRIBED` приходит раньше, чем сервер реально слушает Postgres; готовность — system-сообщение `{extension: "postgres_changes", status: "ok"}` (бывает через 1+ с). `GameRealtime` делает по нему один `refresh()`. В тестах ждать это сообщение, а не `SUBSCRIBED`.

### Фаза 3
- **Сила игрока** — только `playerStrength()` в `src/lib/teams/strength.ts` (сейчас = `level`, в Фазе 5 заменить на рейтинг). `balance.ts` получает уже посчитанную силу. SQL силу не считает: в `add_to_smallest_team` ничья по размеру решается порядком команд `p_team_order`, который сервер сортирует по `playerStrength`.
- **Алгоритм** `balanceTeams` (чистая функция, seed → mulberry32): ёмкости команд ±1 → вратари по одному → жадно сильнейших в самую слабую → попарные обмены по стоимости `gk*1000 + разброс силы*10 + разброс позиций`. «Пересобрать» перебирает до 12 seed, пока расклад не изменится. Тесты: `balance.test.ts`.
- **Видимость:** `private.can_view_teams` — организатор всегда; остальные, если `teams_published_at is not null` или `draft_active`. Статус игры в Фазе 3 не меняется.
- Все изменения составов — только через RPC (`create_team`, `move_player`, `apply_assignments`, …); прямые insert/update/delete запрещены грантами. Каждая RPC обновляет `games.teams_updated_at` — это сигнал Realtime (DELETE-события Realtime не фильтруются по `game_id`, поэтому клиенты слушают строку `games`).
- **Капитан** при назначении попадает в свою команду и закрепляется (`is_locked`). Если капитана перенесли в другую команду или он отказался от игры — `captain_id` сбрасывается (`private.fix_captains`, триггер на `signups`).
- **Драфт:** «змейка» `0,1,2,2,1,0…` (`private.draft_current_team` = `draftTeamIndex` в TS). Выбирает капитан текущей команды или организатор. Когда нераспределённых не осталось — `draft_active = false` и составы публикуются автоматически (иначе игроки перестали бы их видеть сразу после драфта). Удаление команды останавливает драфт.
- Отказ от игры (`going` → не `going`) удаляет игрока из команды триггером `signups_leave_team`. Переведённые из очереди попадают в «не распределены» сами.
- Уровень ставит организатор через `set_player_level` (organizer общей группы); игрок меняет только `name`, `avatar_url`, `position` — гранты на колонки с Фазы 1, дополнительная миграция не понадобилась.
- Цвета — палитра в `src/lib/teams/colors.ts`, в БД hex в нижнем регистре, уникален в пределах игры. Розовый — эмодзи 🩷 (розового кружка нет).
- `@types/node` поднят до 24 (требование Vitest 5; Node в проекте — 24).

### Фаза 4
- **Таймер по меткам:** в `matches` только `timer_status`, `timer_started_at`, `timer_elapsed_ms` (время текущего тайма). Клиент считает `computeElapsed(state, now, offset)` (`src/lib/match/timer.ts`); `offset` = сервер − устройство, меряется один раз (`useServerOffset`, RPC `server_time`, лучший из 3 RTT; гости — из `server_now` в `get_live_game`). По истечении тайма часы показывают `10:00 +01:12` и идут дальше; остановить может только организатор (один сигнал vibrate + beep).
- Команды таймера принимают `p_client_ts` (оценка серверного времени на устройстве; берётся, если не в будущем и не старше 10 мин). Все идемпотентны по состоянию. **Отступление от ТЗ:** вместо одной `timer_next_period` — две: `timer_break(match, period)` и `timer_next_period(match, period)` с номером тайма, иначе повтор из офлайн-очереди перескакивал бы тайм. `applyTimerCommand` в TS повторяет SQL-переходы для оптимистичного UI.
- **Счёт только из событий:** триггер `events_recompute_score` пересчитывает `score_a/score_b` (гол — `team_id`, автогол — сопернику; `team_id` у автогола = команда игрока). События не удаляются — `voided_at`. `computeScore`/`computeStandings` в TS повторяют SQL (сверено тестом live4).
- **`events.id` задаёт клиент** (`crypto.randomUUID`), `add_event` при повторе возвращает существующую строку. `events.second` — секунда **внутри тайма** (+ `period`); подпись минуты `eventMinute()` («12'», «20+2'»). `events.game_id` денормализован для фильтра Realtime.
- `add_event` разрешён в статусах матча `live` и `break` (карточка в перерыве). Правка составов (Фаза 3) разрешена и в статусе игры `live` — иначе опоздавший не сможет забить.
- Права — одна функция `private.can_score_game(game_id)` (сейчас = организатор группы). Первый `timer_start` переводит игру в `live`, закрывает запись и **публикует составы** (миграция `…phase4_publish_on_kickoff`). Одновременно может идти только один матч игры. Команду, у которой есть матчи, удалить нельзя (`team_has_matches`).
- **Офлайн-очередь** (`src/lib/match/queue.ts` + `use-outbox.ts`, IndexedDB `idb-keyval`, ключ `weekball:outbox:<gameId>`): события, отмены и команды таймера идут строго по порядку; сетевые/JWT-ошибки → повтор позже, ошибки валидации → «отклонено» (не блокируют очередь). UI = данные сервера + неотправленные и только что отправленные элементы (до следующего `router.refresh`). Гол сразу виден в счёте, но ~6 с «придержан» (`holdUntil`) для выбора ассиста — так гол записывается за 2 тапа без лишних аннулирований. Отмена неотправленного события просто убирает его из очереди.
- **Публичный live:** `games.live_token` (64 hex), `set_live_link(game, enabled, regenerate)`, `get_live_game(token)` (security definer, anon) отдаёт матчи, события без аннулированных, таблицу и **только id+имя** игроков. Страница `/live/[token]` опрашивает каждые 5 с, OG-заголовок со счётом.
- `finish_game` удаляет неначатые матчи и ставит `games.status = finished`; после этого всё только для чтения.
